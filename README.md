# Bybit Pump/Dump Scanner → Telegram

Бот проверяет рынок Bybit раз в 2 минуты и шлёт в Telegram-канал алерт,
если по монете за последние `WINDOW_MINUTES` минут было движение
≥ `THRESHOLD_PCT`% (по умолчанию 12% за 20 минут — по наблюдению за
максимальным временем движения у конкурентного бота).

Формат сообщения сделан по образцу MEXC-бота со скриншота: направление,
% изменения, MAX/MIN за окно, текущая цена, mark-цена (fair price),
spot-цена (если пара есть и на споте), объём 24ч, сколько минут длится
движение и время по UTC+3.

## Архитектура (бесплатно, без сервера)
GitHub Actions (публичный репозиторий) + cron-job.org (внешний триггер
раз в 2 минуты) + Python-скрипт + Telegram Bot API.

## Шаг 1. Telegram-бот и канал
1. `@BotFather` → `/newbot` → `TELEGRAM_TOKEN`.
2. Создай канал, добавь бота администратором.
3. `TELEGRAM_CHAT_ID` — `@username` канала (если публичный) либо числовой
   chat_id (если приватный, через `getUpdates`).

## Шаг 2. Репозиторий на GitHub
1. Создай **публичный** репозиторий (тогда лимита минут Actions нет вообще).
2. Залей `main.py`, `.github/workflows/scan.yml`, `README.md`, `state.json` (`{}`).

## Шаг 3. Секреты
Settings → Secrets and variables → Actions:
- `TELEGRAM_TOKEN`
- `TELEGRAM_CHAT_ID`

## Шаг 4. cron-job.org — интервал 2 минуты
1. Fine-grained Personal Access Token на GitHub с правом `Actions: Read and write`
   на этот репозиторий.
2. Задача в cron-job.org:
   - URL: `https://api.github.com/repos/<ЮЗЕР>/<РЕПО>/actions/workflows/scan.yml/dispatches`
   - Метод: `POST`
   - Заголовки:
     ```
     Authorization: Bearer <GITHUB_PAT>
     Accept: application/vnd.github+json
     Content-Type: application/json
     ```
   - Тело: `{"ref":"main"}`
   - Расписание: **каждые 2 минуты** (`*/2 * * * *`).

## Почему именно 2 минуты и что с "копипастом" ранов
На 1-минутном интервале ран часто не успевает выполниться и закоммитить
`state.json` до следующего триггера — тогда два рана параллельно видят
одинаковое "старое" состояние и оба шлют один и тот же алерт (дублирование).
Это не лечится условиями внутри `main.py`, потому что проблема на уровне
двух независимых процессов, а не логики одного скрипта.

Решение — блок `concurrency` в `scan.yml`: он не даёт GitHub запускать два
рана параллельно, при столкновении новый ран просто становится в очередь
и стартует сразу после того, как предыдущий закоммитит стейт. Плюс `git pull
--rebase` перед коммитом — на случай гонки при пуше. При интервале в 2 минуты
и лёгком скрипте (один запрос к тикерам на скан) очередь обычно не копится.

## Ограничение по методу обнаружения
Проверка идёт раз в 2 минуты, и между проверками мы полагаемся на свои же
сохранённые снапшоты цены. Если весь пампаж и откат укладываются внутри
одного 2-минутного интервала между проверками — такой всплеск можно не
поймать, это следствие частоты опроса, а не баг скрипта. Как только всплеск
зафиксирован (пересёк порог хоть в одной точке за окно), для точных MAX/MIN
в сообщении скрипт дополнительно подтягивает 1-минутные свечи Bybit за это
окно — так что сами цифры в алерте точные, даже если частота сканирования
грубее, чем у MEXC-ботов, гоняющих раз в минуту.

## Поля, которых нет в этой версии
- **Max size** (как на скрине MEXC) — это, по всей видимости, размер
  крупнейшей сделки/ликвидности в моменте. У Bybit нет прямого аналога в
  публичном REST API тикеров, поэтому поле не добавлено. Можно приблизить
  через стакан (`/v5/market/orderbook`) в момент алерта — скажи, если нужно,
  добавлю отдельным полем.
- **Dex-кнопка** — как на скрине, для этого нужен маппинг символ → контракт
  токена и запрос к DexScreener/GeckoTerminal API. Тоже можно добавить
  отдельным шагом, если пригодится.

## Рынок
Бот смотрит **только USDT-перпетуальные фьючерсы** Bybit (`category=linear`).
Спот сознательно не задействован вообще — движения на споте и на фьючерсах
могут не совпадать (одно есть, другого нет, и наоборот), поэтому раньше
добавленное поле "Spot price" в сообщении убрано, как и отдельный запрос
к споту.

## Настройки (env в scan.yml)
- `WINDOW_MINUTES` — окно поиска движения (по умолчанию 20)
- `THRESHOLD_PCT` — порог срабатывания, % (по умолчанию 12)
- `COOLDOWN_MINUTES` — не дублировать алерт по той же монете (по умолчанию 60)
- `TZ_OFFSET_HOURS` — часовой пояс для времени в сообщении (по умолчанию 3, UTC+3)
